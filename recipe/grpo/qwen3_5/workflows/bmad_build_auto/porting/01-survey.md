## 파이프라인: bmad-build-auto (무인 1회 구현 — clarify → plan → implement → review → HALT)

사람이 하는 일은 한 번뿐이다: 코딩 도구에서 `bmad-build-auto <의도>` 를 호출한다(의도 = 자유 문장, 이슈/티켓 ID, intent 파일 경로, 기존 spec 파일 경로, 또는 `<spec 폴더> + story id`). 그 다음은 사람 개입 없이 끝까지 가거나, `status: blocked` 를 spec 파일에 써 두고 멈춘다. 서브에이전트(구현 1개 + 리뷰어 4개)를 띄울 수 없는 도구에서는 시작 직후 `blocked / no subagents` 로 끝난다.

### 전체 흐름
```
SKILL.md(렌더)  →  workflow.md(활성화)  →  step-01 Clarify&Route  →  step-02 Plan  →  step-03 Implement  →  step-04 Review  →  HALT(done|blocked)
(uv 로 스냅샷 생성)  (훅·사실 로드)        (의도·상태·VCS 확인, spec 경로)  (조사 → spec 작성, 게이트)  (서브에이전트 구현, 검증)  (리뷰어 4개, 분류, 패치/루프백)  (결과 기록, 커밋)
```

- **사람이 넣는 입력**: 호출 프롬프트 한 번(의도). 그 외 질문·승인 지점은 설계상 없음. 대신 사람이 해 둬야 하는 전제가 있음: `uv` 설치, `_bmad/` 설치(config.toml), 깨끗한 git 작업 트리와 알맞은 브랜치, 서브에이전트가 되는 도구.
- **코드를 바꾸는 곳**: step-03(구현 서브에이전트, 미완 마무리, Verification 실패 수정)과 step-04(patch 적용; bad_spec 루프백 시 되돌리고 재구현). 문서 체인: (의도) → `IA/spec-<slug>.md`(ready-for-dev) → 코드 + `{diff_file}` → spec(Review Triage Log, Auto Run Result, deferred) → 커밋.
- **오래된 저장소·사전 준비를 전제한 입력**: `_bmad/config.toml` 와 `_bmad/scripts/render_skill.py`(설치 산출물, SWE 저장소엔 없음); `PA/*` 계획 문서와 `IA/epic-*`·`sprint-status.yaml`(없어도 freeform 경로로 진행); `SPEC.md`+`stories.yaml`(folder+id 모드에서만 필수); 서브에이전트 런타임(없으면 즉시 `blocked`); 깨끗한 작업 트리(SWE 샌드박스는 보통 깨끗하지만 `_bmad/`·`_bmad-output/` 자체가 저장소 안에 생김 — 튜토리얼은 이를 `.git/info/exclude` 에 넣으라고 안내).

## 파이프라인: bmad-build (유인 1회 구현 — clarify → plan → [oneshot | implement → review] → present)

같은 step-file 구조에 사람 체크포인트가 들어간 기본 스킬. 사람은 `bmad-build <의도>` 로 시작하고, 중간에 질문(Open Questions)과 계획 승인(CHECKPOINT 1)에 답하며, 끝에서 요약을 받고 다음 행동(PR, walkthrough)을 고른다. step-02 의 라우트 게이트가 "의도 공백 없음·되돌릴 수 없는 일 없음·작은 변경" 이면 **oneshot**(2개 섹션 spec, 같은 세션에서 구현+리뷰+발표), 아니면 **dispatch**(전체 spec, 승인 후 step-03/04/05).

### 전체 흐름
```
SKILL.md(렌더) → workflow.md → step-01 Clarify → step-02 Plan ─┬─ oneshot ──→ step-oneshot(구현·리뷰·분류·커밋·발표) → 끝
                                                              └─ dispatch ─→ [CHECKPOINT 1 승인] → step-03 Implement → step-04 Review → step-05 Present → 끝
```
단계 간 이동은 코드(step 파일의 NEXT)이지만, step-01 의 다중 목표·VCS 이상, step-02 의 Open Questions 와 CHECKPOINT 1, step-04 의 intent_gap·루프 초과·검증 실패, 서브에이전트 부재 시의 리뷰는 모두 **사람 답을 기다리는 HALT** 다. 마지막은 "Stop and wait for the user".

| | 4c. step-04 Review | `status: in-review`. 리뷰 레이어 3개(Blind Hunter, Edge Case Hunter, Verification Gap)를 서브에이전트로 동시 실행; **불가 시 각 레이어의 완전한 프롬프트를 `IA` 에 써 두고 HALT, 사람이 다른 세션(가급적 다른 LLM)에서 돌려 결과를 붙여 넣게 함**. 분류·라우팅은 build-auto 와 동일. intent_gap → 코드 되돌리고 **사람에게 루프백**, 해결되면 step-02 부터 재실행; bad_spec → 되돌리고 spec 수정 후 step-03 재실행(5회 초과 **HALT 사람 에스컬레이션**); patch → 구현 서브에이전트 재호출(불가 시 직접), Verification 재실행(실패 수정 불가면 **HALT**); defer → `IA/deferred-work.md` | `{diff_file}`, spec, `R/review-prompts/*`, **리뷰 서브에이전트 3개**, **사람(HALT 시)** | **코드 변경**(패치/되돌림), spec(`## Review Triage Log`, `## Spec Change Log`), `IA/deferred-work.md` |
| | 5. step-05 Present | `status: done`, sprint-status 를 `review` 로 동기화(있을 때). git 있고 더러우면 **로컬 커밋**(conventional message), 절대 auto-push 금지. `open_spec` 훅(기본 비움). 1–2문장 요약(변경·리뷰 결과·커밋 해시). 다음 행동 한 줄 제안(PR 생성, `bmad-walkthrough`, 다른 변경). `on_complete` 훅 | spec, git | 로컬 커밋, 채팅 요약 |

### 정리하면
- **사람이 넣는 입력**: 호출 프롬프트; (필요 시) 서브에이전트 허가 1회; step-01 의 재개/신규 선택, VCS 이상 처리, Split/Keep; step-02 의 토큰 Split/Keep, Open Questions 답변 전부, CHECKPOINT 1 승인(계속/중단/리뷰); step-03/oneshot 의 매트릭스 모호성·간단하지 않은 패치 판단; step-04 의 intent_gap 해결, 루프 초과·검증 실패 에스컬레이션, 서브에이전트 없을 때 리뷰 프롬프트를 직접 돌려 결과 붙여넣기; 끝의 다음 행동 선택.
- **코드를 바꾸는 곳**: oneshot(직접) 또는 step-03(핸드오프/직접) + step-04(patch, 되돌림). 문서 체인: (의도) → `IA/spec-<slug>.md`(draft → ready-for-dev → in-progress → in-review → done) → 코드 + `{diff_file}` → spec(Triage/Change Log) → `IA/deferred-work.md` → 커밋.
- **오래된 저장소·사전 준비를 전제한 입력**: build-auto 와 동일(`_bmad/` 설치, uv, 깨끗한 트리) + `IA/sprint-status.yaml`·epic 문서(프로젝트 경로에서 온 것, 없으면 생략) + 서브에이전트 없는 도구에서는 리뷰를 사람이 수동 중계해야 함.

## 파이프라인: 스펙 기반 epic (bmad-spec → bmad-build ×N → bmad-retrospective)

여러 세션이 필요한 한 가지 결과물을 위한 경로. 사람이 세 스킬을 차례로, 각각 **새 채팅**에서 호출한다.

### 전체 흐름
```
bmad-spec <의도> (+ Story Breakdown)  →  bmad-build "story k from <spec>/stories.yaml" ×N  →  bmad-retrospective <spec 폴더>
(5필드 SPEC.md + stories.yaml)            (스토리마다 위 bmad-build 파이프라인 1회)         (증거 읽고 수용 판정)
```
각 단계는 사람이 다음 스킬을 호출해야 넘어간다. bmad-spec 는 대화형이면 질문·확인, 헤드리스면 JSON 으로 끝난다; Story Breakdown 은 **대화형 전용**이고 스토리마다 체크포인트 여부를 사람에게 묻는다.

### 단계별 입력·출력

| 명령 | PHASE | 하는 일 | 입력 | 출력 |
|---|---|---|---|---|
| **1. bmad-spec `<의도>`** | 1. 활성화·모드 | `resolve_customization.py`, `resolve_config.py` 실행. TTY 없음·프로그램 호출·입력 완비면 **headless**, 아니면 interactive(인사, party-mode·elicitation 안내) | `_bmad/config*.toml`, `plan/bmad-spec/customize.toml` | (없음) |
| | 2. Operation | 입력을 5필드 커널(Why / Capabilities(CAP-N intent+success) / Constraints / Non-goals / Success signal)로 증류. 풍부한 입력은 질문 없이, 빈약하면 express(공백→open_questions) 또는 guided(**사람과 필드별 대화**) 선택. 결정마다 `memlog.py append` 로 `.memlog.md` 에 기록; SPEC.md 는 그 로그에서 **도출** | **사람의 의도/문서**, `assets/spec-template.md`, 기존 `.memlog.md`(갱신 시) | `_bmad-output/specs/spec-<slug>/{SPEC.md, .memlog.md, <companion>.md}` |
| | 3. Self-Validate | Spec Law 8규칙 점검(1차 일관성, 2차 보존), 판정을 memlog 에 event 로 기록, interactive 면 **사람과 검토** | 위 산출물 | `.memlog.md` 추가 |
| | 4. Story Breakdown(선택, interactive 전용) | 역량·제약을 **사람과 함께** 독립 배포 가능한 조각으로 나누고, 스토리마다 `spec_checkpoint`/`done_checkpoint`/`invoke_dev_with` 를 **사람에게 물음** | SPEC.md, **사람의 답** | `spec-<slug>/stories.yaml`(순서 있는 목록; id 는 따옴표 문자열) |

| **3. bmad-retrospective `<spec 폴더>`** | 1. Gather | `stories.yaml` 을 재고로, 각 `stories/<id>-*.md` 의 status 로 완료 여부 판정(미완료면 **사람에게 계속할지 물음**; `-H` 면 기록 후 진행). `git_evidence.py` 로 diff 범위·커밋 수집 | `SPEC.md`, `stories.yaml`, `stories/*.md`, git | `<spec 폴더>/RETROSPECTIVE.md`(뼈대) |
| | 2. Analyze | 집계 결함(중복·god class·패턴 이탈), `bmad-review` 코드 렌즈로 diff 리뷰, 동작 변경 시 E2E 로 실제 실행. 출처 없는 finding 은 버림 | diff, 코드 | RETROSPECTIVE.md(findings) |
| | 3. Team Discussion(선택) | 사람이 요청할 때만 `bmad-party-mode` | — | — |

### 정리하면
- **사람이 넣는 입력**: 세 스킬 호출; bmad-spec 의 의도(+guided 모드 답, 자기검증 검토, 스토리 분해 대화와 체크포인트 선택); 스토리마다 bmad-build 의 모든 체크포인트; retrospective 의 미완 처리·override·액션 아이템 채택.
- **코드를 바꾸는 곳**: 2단계(bmad-build)뿐. 문서 체인: (의도) → `.memlog.md` → `SPEC.md`(+companions) → `stories.yaml` → `stories/<id>-*.md` → 코드 → `RETROSPECTIVE.md`.
- **오래된 저장소·사전 준비를 전제한 입력**: `_bmad/` 설치와 uv(세 스킬 모두 스크립트 호출); `uv` 로 도는 `memlog.py`·`git_evidence.py`·`sprint_status.py`; 스토리 분해는 TTY 와 사람이 있어야 함; 한 이슈를 여러 스토리로 나눌 이유가 없는 SWE 과제엔 과함.

## 파이프라인: 레거시 스토리 루프 (bmad-create-story → bmad-dev-story → bmad-code-review, v6 shim)

v6.11 에서 폐기되어 `v6-shims/` 에 "전체 보존" 된 옛 Phase 4 루프. 신규 설치에선 `--shims` 를 줘야 깔린다. 사람이 세 스킬을 차례로 호출한다.

### 전체 흐름
```
bmad-create-story [epic-story]  →  bmad-dev-story [story 파일]  →  bmad-code-review [story 파일]
(epics·PRD·architecture → 스토리 파일)   (Tasks/Subtasks 를 TDD 로 끝까지 구현)   (리뷰어 4개, 분류, 패치 여부를 사람이 선택)
```
사람이 다음 스킬을 호출해 넘긴다. dev-story 는 "마일스톤·세션 경계로 멈추지 말고 완료까지 계속" 이 규칙이지만 HALT 조건(모호한 task, 새 의존성, 3회 연속 실패, 설정 파일 없음, 회귀 실패)에서는 사람에게 묻는다.

### 단계별 입력·출력

| 명령 | PHASE | 하는 일 | 입력 | 출력 |

| | 2–3. Review·Triage | 레이어 4개(Blind Hunter, Edge Case Hunter, Verification Gap, Acceptance Auditor[spec 있을 때]) 서브에이전트 동시 실행(불가 시 프롬프트를 `IA` 에 쓰고 **HALT**), verdict 부여, decision_needed / patch / defer 라우팅 | `{diff_file}`, spec, **리뷰 서브에이전트** | findings 목록 |

### 정리하면
- **사람이 넣는 입력**: 세 스킬 호출; create-story 의 대상 선택(sprint-status 없을 때); dev-story 의 HALT 응답과 끝의 설명 요청; code-review 의 대상·spec 확인·진행 확인·decision-needed 결정·패치 적용 방식·다음 행동.
- **코드를 바꾸는 곳**: dev-story 5–8(TDD 루프, 새 테스트 포함)과 code-review 4(사람이 적용을 고를 때). 문서 체인: `PA/epics.md`(+prd/architecture) → `IA/<story_key>.md`(ready-for-dev → in-progress → review → done) → 코드 → `### Review Findings` → `IA/deferred-work.md`; 상태는 `IA/sprint-status.yaml` 에 병행 기록.
- **오래된 저장소·사전 준비를 전제한 입력**: `PA/epics.md`·PRD·architecture(프로젝트 계획 경로 산출물; SWE 저장소엔 없음), `IA/sprint-status.yaml`(bmad-sprint-planning 산출물), `--shims` 설치, uv 스크립트, 인터넷(create-story 4단계), 리뷰 서브에이전트.

## Normal use

**Prerequisites and install.** Node.js 20.12+, Python 3.10+, `uv` (`README.md:18`); `uv` is a hard requirement for `bmad-build` and `bmad-build-auto` because they render through `render_skill.py` and HALT without it (`docs/start/install-bmad.md:21-23`, `tools/installer/core/uv-check.js:9-12`). `npx bmad-method install` (`README.md:21`), or headless `npx bmad-method install --yes --modules bmm --tools claude-code` (`docs/start/install-bmad.md:105`, same command in both tutorials `docs/start/build-your-first-change.md:37`, `docs/existing-codebases/getting-deeper.md:72`). node/npm are not used here and no install was run; what follows is read from the installer source.

The installer writes, inside the project root:
- `_bmad/` with `_config/` (manifest.yaml, files-manifest.csv, bmad-help.csv, skill-manifest.csv), `core/`, `scripts/`, `custom/` (`tools/installer/core/install-paths.js:18-34`, `:54-67`; folder name `tools/installer/ide/shared/path-utils.js:21`).
- `_bmad/config.toml` (team scope: `[core]`, `[modules.bmm]`, `[agents.*]`) and `_bmad/config.user.toml` (user scope) (`tools/installer/core/manifest-generator.js:428-437`, `:553-593`), plus empty `_bmad/custom/config.toml` and `config.user.toml` stubs (`:647-671`). Keys come from `src/core-skills/module.yaml` (`user_name`, `project_name`, `communication_language`, `document_output_language`, `output_folder` default `_bmad-output`, `:8-33`) and `src/bmm-skills/module.yaml` (`user_skill_level`, `planning_artifacts` default `{output_folder}/planning-artifacts`, `implementation_artifacts` default `{output_folder}/implementation-artifacts`, `project_knowledge` default `docs`, `:13-41`). `{output_folder}` is the only directory created at install (`src/core-skills/module.yaml:35-38`).
- `_bmad/scripts/` = a copy of `src/scripts/*.py` without tests (`tools/installer/core/installer.js:712-730`).
- One directory per skill, copied **verbatim** (SKILL.md and every sibling file, no transformation) into the tool's skills directory (`tools/installer/ide/_config-driven.js:408-410`, `:462`): `.claude/skills/` for Claude Code, `.agents/skills/` for Cursor/Windsurf/Codex and most others (`docs/reference/skills-and-agents.md:29-39`). Deprecated shims are opt-in on fresh installs (`--shims`, `CHANGELOG.md:33`, `tools/installer/core/shim-policy.js:92-99`).

**Driving it.** A skill is "a named command the installer places in your AI tool. Type its name … On some platforms the name takes a `/` or `$` prefix" (`docs/reference/skills-and-agents.md:12`). The alternative is loading an agent persona (`bmad-agent-dev` = Amelia) and typing a menu code; `BD` dispatches `bmad-build` (`docs/reference/skills-and-agents.md:48-56`, `src/bmm-skills/agents/bmad-agent-dev/customize.toml:58-61`, menu dispatch `SKILL.md:68-74`). `bmad-help` reads `_bmad/_config/bmad-help.csv` and the artifact folders to recommend the next skill (`core/bmad-help/SKILL.md:25-29`); the catalog rows say Build is `ship` phase, preceded by `bmad-sprint-planning`, followed by `bmad-code-review`, output in `implementation_artifacts` (`src/bmm-skills/module-help.csv:4`).

**What the agent does on `bmad-build` / `bmad-build-auto` activation.** `SKILL.md` is 13 lines: run `uv run --no-cache {project-root}/_bmad/scripts/render_skill.py --project-root … --skill {skill-root}` exactly once; on success "read and follow the one absolute `workflow.md` instruction printed to stdout"; on failure report and HALT, "Do not run any workflow source directly" (`ship/bmad-build/SKILL.md:6-13`, identical in `ship/bmad-build-auto/SKILL.md:6-13`). The renderer loads every `*.md` in the skill dir except `SKILL.md` (`workflow.md` required, `src/scripts/render_skill.py:98-115`), merges the four central TOML layers (`src/scripts/config_utils.py:98-107`) and the three customization layers (`:110-119`), substitutes `{{.key}}` (unique key anywhere in the merged config, `render_skill.py:140-150`), `{{config.path}}`, `{workflow.field}` (lists → markdown list or `_None._`, review layers → `#### Name (id)` sections, `:153-175`) and `[[bmad-snapshot:file.md]]` → the absolute path of that file inside the snapshot (`:232-267`), and publishes an immutable generation at `{project-root}/_bmad/render/<skill>/<slug>-<roothash>/<generationhash>/` with `manifest.json` (`:358-379`); it prints `read and follow <…>/workflow.md` or `HALT: <error>` (`:394-396`). It refuses to run if `{project-root}/_bmad/` does not exist (`:325-326`).

**Worked example, one-session change (from the docs).** In a Django 5.2.4 checkout: install, add `/_bmad/`, `/_bmad-output/`, `/.claude/`, `/uv.lock` to `.git/info/exclude`, open Claude Code, type `/bmad-build Add JSON output support to django-admin diffsettings. Preserve the existing output formats, add focused tests, and update the command documentation. Leave the implementation in the working tree for local inspection.` (`docs/existing-codebases/getting-deeper.md:72-99`). "Build asks any questions it needs before it writes a plan … presents a plan and waits for you to approve it … builds and reviews the change, handles its findings, and shows you the result … ends with a short summary and offers the next steps" (`:101-111`). Other accepted intents: a bare issue link `/bmad-build Fix https://github.com/org/repo/issues/42.`, an intent file, a ramble, or `/bmad-build` alone followed by "What would you like to do?" (`docs/build/build-a-change.md:43-66`). Result: modified source, passing tests if a suite exists, a local conventional commit, an implementation record beside the parent spec (`docs/build/build-a-change.md:130-134`); follow-ups land in `deferred-work.md` (`:141-147`).

**Worked example, unattended.** `bmad-build-auto` takes the same intents plus a spec path or `<spec-folder> + story id` (`docs/build/autonomous-development-loops.md:43-49`); it "clarifies, plans, implements, and reviews one intent or story, then exposes a terminal status" (`:8-11`), halts `blocked / no subagents` without subagents (`:30-33`), commits but does not push, leaves a clean working copy (`:192`), and writes `{implementation_artifacts}/spec-<slug>.md` or, before a spec exists, `bmad-build-auto-result-<slug-or-timestamp>.md` (`:228-262`). Orchestrators (bmad-loop, an AI session) read `status`, `blocking condition`, `deferred` from the file rather than chat (`:271-282`).

## Machinery the text relies on

- **Scripts**: `uv run --no-cache {project-root}/_bmad/scripts/render_skill.py …` as the very first action of build/build-auto; no fallback ("Do not run any workflow source directly", `ship/bmad-build-auto/SKILL.md:12-13`). Non-rendered skills run `uv run …/resolve_customization.py --key workflow` and `uv run …/resolve_config.py` (with a "read the three TOML files yourself" fallback, e.g. `ship/bmad-code-review/SKILL.md:24-32`, `:44`); bmad-spec runs `memlog.py` for every decision (`plan/bmad-spec/SKILL.md:59-63`); retrospective runs `git_evidence.py` and `sprint_status.py` (`ship/bmad-retrospective/SKILL.md:50-52`). Inside the build steps the agent is told to use "the repository's version-control tooling" to write a unified diff since the baseline, untracked files included, to a temp file (`ship/bmad-build-auto/step-03:38`), and to run the spec's own `## Verification` commands (`:40`).
- **Config**: `_bmad/config.toml` + `config.user.toml` + `_bmad/custom/config*.toml` (four layers, `src/scripts/config_utils.py:98-107`); per-skill `customize.toml` + `_bmad/custom/<skill>.toml` + `.user.toml` (`:110-119`); `spec` frontmatter `context:` list of extra docs the implementer must load (`ship/bmad-build-auto/spec-template.md:8`, `customize.toml:42`). Project context is expected in `AGENTS.md` (`plan/bmad-spec/customize.toml:23-26`).
- **Subagents** (the central dependency): build-auto — compile-epic-context (`step-01:59`), investigation (`step-02:11`), implementation handoff (`customize.toml:39-45`, `step-03:30`), four review layers (`step-04:25-27`); "Using subagents when instructed is mandatory. If you cannot, HALT with status `blocked` and blocking condition `no subagents`" (`workflow.md:53`), never backgrounded (`:55`). build — implementation falls back to "implement directly from the spec" (`ship/bmad-build/step-03:33`), epic context falls back inline (`step-01:63`), but review layers without subagents → write the prompts to `IA` and HALT for a person (`step-04:27`, `step-oneshot:35`). The reviewers must run "at the same model capability as the current session" (`step-04:6`). Reviewer prompts forbid nested skills/subagents and tool-routed findings (`customize.toml:69`, `:85`).
- **Hooks / extensions**: `activation_steps_prepend/append`, `persistent_facts`, `on_complete`, `open_spec` (build only), `implementation_handoff`, `review_layers` / `oneshot_review_layers` — all empty or default in the shipped `customize.toml` (`ship/bmad-build/customize.toml:13-32`, `:61`; `ship/bmad-build-auto/customize.toml:13-32`); merge rules in `docs/customize/customize-bmad.md:64-82`.
- **Network**: none in build / build-auto step text. `bmad-code-review` resolves PR references with `gh pr view` (`ship/bmad-code-review/steps/step-01:23`); `bmad-create-story` step 4 does "Web research for latest technical specifics" (`shims/bmad-create-story/SKILL.md:326-334`); `bmad-deep-recon` runs web searches (`docs/reference/skills-and-agents.md:138`); `bmad-help` may fetch module docs URLs (`core/bmad-help/SKILL.md:29`). The docs' example intents include GitHub issue URLs (`docs/build/build-a-change.md:48`).
- **Git**: build-auto requires a clean tree, a fitting branch and writable metadata (`git add --refresh -- .`) before planning (`step-01:74`); captures `baseline_revision` = HEAD (`step-03:20`); diff since baseline for verify and review (`step-03:38`, `step-04:15`); "Do NOT `git add` anything" during review staging (`step-04:19`); reverts code on intent_gap/bad_spec (`step-04:71-72`); at the end commits every reviewed file (+ spec if tracked), verifies the working copy is clean, never pushes (`step-04:109-114`, `docs/build/autonomous-development-loops.md:192`). build: same baseline/diff, "No push. No remote ops." (`ship/bmad-build/step-03:9`), VCS sanity HALT (`step-01:80`), local commit at present (`step-05:21`, `step-oneshot:83`), "NEVER auto-push" (`step-05:9`).
- **Artifacts in the repo**: everything lands under the project root — `_bmad/` (config, scripts, `render/` snapshots), `_bmad-output/{planning,implementation}-artifacts/` (`src/core-skills/module.yaml:30-33`, `src/bmm-skills/module.yaml:28-36`), `_bmad-output/specs/` (`plan/bmad-spec/customize.toml:45`), the skills dir (`.claude/skills/`). The tutorial excludes them with `.git/info/exclude` (`docs/existing-codebases/getting-deeper.md:75-83`). The diff file and claims file go to the system temp dir (`ship/bmad-build-auto/step-03:38`).
- **Interactive points**: build-auto: none (replaced by `blocked`, see Processes A). build: listed in Processes B; the strongest are CHECKPOINT 1 (`ship/bmad-build/step-02:52-58`), Open Questions (`:34`), the resume/new question (`step-01:31-38`), and the review fallback that needs a person to run prompts elsewhere (`step-04:27`). All other skills greet the user and ask at their first step (e.g. `ship/bmad-code-review/steps/step-01:54`, `plan/bmad-project-context/SKILL.md:12`).
- **Language / persona tokens**: every step says "Speak in `{{.communication_language}}` … write files in `{{.document_output_language}}`" (`ship/bmad-build-auto/step-01:12`); the value comes from `config.toml` (default English, `src/core-skills/module.yaml:19-28`).

## Recommendation

Port **A, `bmad-build-auto`** — the rendered chain `workflow.md → step-01 → step-02 → step-03 → step-04 → HALT` with `spec-template.md`, the four review-layer instructions and the implementation handoff from `customize.toml`, and the two reviewer prompt files. Reasons: it is the upstream's own answer to "no human in the loop" (every `ask` of `bmad-build` is already replaced by a rule or a `blocked` status, so stage 2's G2/G4 rows are few and mostly about *what to do instead of blocking*); its spec carries a Code Map, Given/When/Then acceptance and a `## Verification` command list that map onto running the repo's tests; its review-then-patch loop is the part of BMad that differs most from the ports already registered (spec-kit, OpenSpec, AI-DLC, Agent OS), which matters for the variation pipeline. The attended `bmad-build` is the canonical default (`README.md:24`, `docs/build/build-a-change.md:8`), the same precedent the OpenSpec port faced (ff vs propose); its oneshot route is lighter but carries five more human gates.

Proposed workflow name: **`bmad_build_auto`** (`bmad_build` if the user prefers the attended skill as the base).

Points the user should settle before stage 2 reads the gaps (not decisions yet):
1. Base on `bmad-build-auto` (unattended, four review layers incl. intent-alignment) or on `bmad-build`'s oneshot/dispatch text (adds Open Questions and CHECKPOINT 1 that would have to be rewritten)?
2. Subagents: upstream's single-agent fallback for review exists only in `bmad-review` ("Otherwise run the lenses sequentially yourself", `core/bmad-review/SKILL.md:32`) and `docs/build/review-a-change.md:151-155`, not in the build steps. Is "run each layer inline, in order, then triage" the acceptable reading, or should review be dropped?
3. `blocked` outcomes (`intent gap`, `unclear intent`, verification failure, loop > 5): keep the upstream HALT (ends the rollout with no patch) or follow the speckit_bug precedent (assume, record, continue)?
4. Repo hygiene: the clean-tree gate, the final commit and "working copy clean" check, and the in-repo `_bmad/`, `_bmad-output/` locations versus the verifier's `git add -A` and the no-commit convention of earlier ports.
5. The renderer: emulate `render_skill.py`'s substitutions at build time (no `uv` in the sandbox) or ship `_bmad/` + `uv` into the image as the openspec port did with its CLI.
